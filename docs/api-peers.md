# Peers API — контракт для клиента

Все клиентские ручки пиров говорят **только в AGW-конверте** и **только POST**.
Плейн-JSON тела нет вовсе: запрос без `keyPayload` отбивается `400 keyPayload missing` —
именно так приложение отличает «наш api» от чужого.

Причина: `subscription_id`, `peer_id`, `device_id` не попадают ни в query string, ни в путь,
значит их нет в access-логах, в истории браузера и в крэш-репортах.

## Конверт

Запрос:

```json
{
  "keyPayload": "<base64(RSA-PKCS#1v1.5({aes_key, aes_iv, aes_salt}))>",
  "apiPayload": "<base64(AES-256-CBC(JSON тела, IV = aes_iv[0..16], PKCS#7))>"
}
```

Ответ — **не** JSON, а сырые байты AES-256-CBC с тем же `aes_key` и `aes_iv[0..16]`.
Заголовки авторизации не нужны: подлинность обеспечивает RSA-ключ api.

Публичная часть ключа апи: `agw_public.pem` (в приложении уже используется для `/v1/config`).
Готовый образец — `dopamine/test_agw_encryption.py`.

## Клиентские ручки (конверт, POST)

| ручка | тело | ответ |
|---|---|---|
| `POST /v1/locations` | `{subscription_id}` | `{access: [...], pools: [...]}` |
| `POST /v1/peers` | `{subscription_id, device_uid, device_name?, card_id, public_key?, label?}` (ручной/админский вариант: `env`+`proto` вместо `card_id`) | `{peer: PeerView, support_tag, pools: [...]}` |
| `POST /v1/peers/prepare` | `{subscription_id, device_uid, public_key, device_name?, platform?, pools?: ["<shard>:<pool>", …]}` | `{prepared: [PreparedPeer], skipped: [{card_id, reason}]}` |
| `POST /v1/peers/list` | `{subscription_id, device_uid?}` | `{peers: [PeerView]}` |
| `POST /v1/peers/delete` | `{subscription_id, peer_id}` | `{status: "ok"}` |
| `POST /v1/devices/list` | `{subscription_id}` | `{devices: [DeviceView]}` |
| `POST /v1/devices/update` | `{subscription_id, device_id, device_name?}` | `{device: DeviceView}` |
| `POST /v1/devices/delete` | `{subscription_id, device_id}` | `{status: "ok"}` |

`PeerView`:

```json
{ "peer_id": "…", "device_id": "…", "env": "standard-eu", "proto": "amnezia_peer",
  "card_id": "standard-eu:eu:amnezia_peer",
  "address": "10.88.0.2/32", "label": null, "created_at": "…",
  "revoked_at": null, "revoke_reason": null }
```

`card_id` — карточка (`<шард>:<пул>:<протокол>`), под которую создан пир. По ней
приложение собирает конфиг из списка пиров без похода в api: адрес берётся из
блока шарда, а endpoint, серверный ключ, MTU, DNS и обфускация — из ноды этого
пула. `card_id = null` у пиров, созданных до появления `peers.pool` (миграция
`0025`) и у ручной формы `env` + `proto`: для них приложение берёт карточки из
`POST /v1/locations`.

`PeerCreateResponse` — то же плюс `support_tag` (строка вида `7K2M-9XQ4P`) и `pools[]`
с `endpoint` / `server_public_key` / `mtu` / `dns` / `keepalive` / `obfuscation`.

### `POST /v1/peers/prepare` — все пулы гранта за один вызов

Приложение зовёт ручку при логине устройства / импорте подписки, чтобы сохранить конфиги
всех пулов сразу: спид-тест идёт по ним, не дожидаясь первого подключения.

```json
{
  "subscription_id": "…", "device_uid": "…",
  "public_key": "<base64 X25519>",
  "device_name": "iPhone", "platform": "ios",
  "pools": ["standard-eu:eu", "standard-eu:prem"]
}
```

`pools` необязателен: без него берутся **все peer-карточки** гранта. Значение — тот же
handle, что `card_id`, без протокола (`<shard>:<pool>`); запрошенный, но несуществующий
handle возвращается в `skipped` с `reason: "unknown_pool"`.

Ответ (200; отдельные пулы не валят запрос):

```json
{
  "prepared": [
    { "card_id": "0001:eu:amnezia_peer", "pool": "eu", "proto": "amnezia_peer",
      "address": "10.88.0.2/32", "peer_id": "…",
      "config": { "card_id": "0001:eu:amnezia_peer", "pool": "eu",
                  "country": "NL", "country_name": "Netherlands",
                  "proto": "amnezia_peer", "kind": "peer", "nodes": [ … ] } }
  ],
  "skipped": [
    { "card_id": "0001:eu:hysteria2", "reason": "card_kind_not_peer" },
    { "card_id": "0001:ru:amnezia_peer", "reason": "peers_limit" }
  ]
}
```

`config` — та же карточка, что `/v1/locations`/`pools[]` (`endpoint`, `server_public_key`,
`mtu`, `dns`, `keepalive`, `obfuscation`, `payload`), поэтому клиент парсит один формат.

Правила:

1. **Только peer-карточки.** `client_config` (hysteria2) не готовится: `skipped` с
   `card_kind_not_peer` — конфиг клиент собирает из `nodes[].payload`.
2. **Идемпотентность** по `(env, pool, public_key)`: живой пир с этим ключом в этом пуле
   возвращается как есть (`prepared`, тот же `peer_id` и адрес), новый не создаётся.
3. **Лимиты как у одиночного создания**: per-(device, pool) — 3 (считается по
   `devices.public_key`, все каналы устройства), подписного лимита нет (`0` = без лимита,
   с 0.7.39). Пул за лимитом → `skipped: "peers_limit"`, остальные пулы провижнятся.
4. **Грант**: `check_grant` на каждый протокол; отказ (`proto_not_granted`, `grant_expired`,
   `quota_exhausted`, `no_grant`) уходит кодом в `skipped` этого пула.
5. **Изоляция пулов**: каждый `INSERT` — своя транзакция; ошибка БД одного пула → `skipped:
   "db"` (конфликт адреса/ключа ретраится со следующим свободным адресом), остальные пишутся.
6. В отличие от `POST /v1/peers`, общий HTTP-статус 200 даже когда часть пулов пропущена;
   причину каждого смотреть в `skipped[].reason`.

`DeviceView`: `{id, device_uid, device_name, support_tag, created_at, rotated_at}`.

## Панель управления (без конверта)

Эти ручки — для сайта и админки, авторизация `Authorization: Bearer <service token>`,
обычный JSON. Приложение их не вызывает.

| ручка | назначение |
|---|---|
| `GET /v1/access?subscription_id=…` | гранты подписки |
| `POST /v1/access` | выдать/продлить грант (`plan` или фиксированный `env`) |
| `DELETE /v1/access` | отозвать грант |
| `GET /v1/access/capacity?plan=…` | ёмкость шардов плана |
| `GET /v1/admin/support/{tag}` | подписка/устройство по `support_tag` |

## Активация

`POST /v1/activate` — плейн JSON, как и `/v1/key/activate`: это ручка сайта, у которого
нет AGW-клиента. Тело то же, что у старой активации.

## Ошибки

Тело ошибки уходит **внутри конверта**, как и успешный ответ:

```json
{ "error": "quota_exhausted" }
```

| код | `error` | HTTP |
|---|---|---|
| ключ не base64/не X25519 | `bad_public_key` | 400 |
| нет гранта на env / протокол | `no_grant`, `proto_not_granted` | 403 |
| env не обслуживается | `env_not_served` | 403 |
| срок вышел | `grant_expired` | 402 |
| квота | `quota_exhausted` | 402 |
| туннелей на устройство больше 3 (по всем подпискам) | `peers_limit` | 409 |
| туннелей на подписку больше 45 | `subscription_limit` | 409 |
| устройств на подписку больше 15 | `devices_limit` | 409 |
| ключ уже занят в env | `key_taken` | 409 |
| нет свободного адреса | `no_free_address` | 503 |
| пиры выключены | `peers_disabled` | 404 |

Ёмкость шарда считается **в адресах**, а не в подписках: лимит шарда = сумма блоков env из
`env_networks` минус резерв 10% (`no_free_address` приходит на 90% блока, а не на последнем
адресе). `/v1/capacity?plan=` отдаёт `used`/`limit` в адресах; `max_subscriptions` в
`env_capacity` — админский override, если нужно ограничить шард жёстче. Один `/24` = 253 пира,
из них раздаются 227.

## Лимиты

| лимит | на что | по умолчанию | код отказа |
|---|---|---|---|
| `peers_per_device` | живые туннели **одного физического устройства** в одном пуле | 3 | `peers_limit` |
| `max_devices_per_subscription` | устройства (установки) одной подписки | 15 | `devices_limit` |
| `max_per_subscription` | живые туннели одной подписки | 0 (без лимита) | `subscription_limit` |

**Лимит туннелей — на устройство и на пул, а не на подписку.** Устройство опознаётся по своему
X25519-ключу (`devices.public_key`, он же `device_public_key` в терминах клиента): считаются
живые пиры всех записей `devices` с этим ключом, но **в разрезе одного `(env, pool)`**.
Поэтому `POST /v1/peers/prepare` кладёт по одному пиру в каждый пул гранта: три туннеля в
`eu` не мешают туннелю в `ru`. Роутер, которому нужно три туннеля в одном пуле для failover,
упирается в 3 ровно тогда, когда их три в этом пуле. Пиры дополнительных каналов роутера
(свой `public_key` + `label`) принадлежат той же записи устройства и считаются в тот же
лимит. Отозванные и истёкшие пиры не считаются: удалённый туннель сразу освобождает слот.

`peers_per_device` задаётся в `[service.peers]` конфига api (старое имя `max_per_device`
продолжает читаться; `0` или отсутствие ключа = 3). Значение из `subscription_limits`
(`peers_per_device`, `peers_per_subscription`) перекрывает дефолты для этой подписки.

`devices_per_subscription` остаётся отдельным лимитом на число записей `devices` (экран
устройств) и проверяется только при регистрации нового устройства: оно не отказывает уже
известному устройству в новом туннеле, поэтому с лимитом на устройство не конфликтует.

## Идемпотентность

`POST /v1/peers` с тем же `(env, pool, public_key)` возвращает существующий пир — повтор после
таймаута безопасен. `pool` входит в ключ идемпотентности: одна и та же пара ключей может
держать по туннелю в каждом пуле шарда (`POST /v1/peers/prepare`), но в одном пуле это один
и тот же туннель. Идемпотентный поиск идёт **до** проверки лимитов: повтор запроса на
устройстве, у которого лимит уже выбран, получает `200` с тем же пиром, а не `409`.

## Клиент не видит шард: карточка — это handle

Ответы наружу (`/v1/locations`, `/v1/peers*`, `/v1/access`) **не содержат `env`**: карточка
локации отдаётся как

```json
{ "card_id": "0001:eu:amnezia_peer", "pool": "eu", "pool_translation": {...},
  "proto": "amnezia_peer",
  "nodes": [ {"endpoint": "…", "country": "NL", "server_public_key": "…", "mtu": 1280} ] }
```

`card_id` — `<шард>:<пул>:<протокол>`; приложение возвращает его в `POST /v1/peers`
(`{"card_id": "0001:eu:amnezia_peer", ...}`), api сам разворачивает его в `(env, proto)`.
Так шард остаётся деталью сервера, а не экраном. Ручной/админский вызов может по-прежнему
передать `env` и `proto` раздельно.

`country` / `country_name` на карточке — страна **пула**, а не машины: её объявляет нода в
конфиге (`[node] pool_country_code` / `pool_country_name`, миграция `0026`), потому что один
пул может стоять в нескольких странах (парк DE+NL продаётся одной локацией). Флаг и подпись
в списке приложение берёт отсюда и не разбирает hostname. Пул, который ничего не объявил,
падает на `country` своей первой ноды — карточка без флага выглядит сломанной.
`nodes[].country` остаётся ISO-кодом конкретной машины: он нужен, когда ноды пула стоят в
разных странах и это важно показать.

`nodes[]` — один элемент на **entry-адрес**: нода, объявившая несколько точек входа
(`[[node.endpoints]]`, например основной и запасной IP), даёт по элементу на каждый, с
одинаковыми `server_public_key` / `mtu` / `dns` / `obfuscation` и разными `endpoint`. Одна
карточка из двух машин, у одной из которых два IP, — это три endpoint, и приложение вправе
выбрать любой.

Каждый элемент несёт ещё и `endpoints` — тот же адрес в единой форме
(`[{"ip": "…", "port": 443, "weight": 100}]`, см. `[[node.endpoints]]`); `endpoint`
(`"ip:port"`) остаётся для старых клиентов, `endpoints[].weight` — вес адреса в пуле.

## Шарды: `env` — непрозрачный id

`env` — идентификатор шарда, а не описание: `0001`, `0002`, а не `standard-ru`. Имя несётся
**дословно** везде — в конфиге ноды, в `env_networks` / `env_capacity` / `subscription_access`,
в `access[].env`, `peer.env` и в топике пиров. Топик привязан к пулу:
`peers-update-<env>-<pool>` (нода без `pool` в конфиге остаётся на env-wide `peers-update-<env>`),
потому что один ключ устройства держит по адресу на пул. Никакого префикса `custom` больше
нет: раньше неизвестное имя превращалось в `Env::Custom` и в базу уезжало `customstandard-01` —
шард, которого не обслуживает ни одна нода.

План живёт в `env_capacity.plan`, локации — в `pools`, человеческое имя — в `env_capacity.title`.
Вид шарда — `env_capacity.kind`: `core` (наш регион, может быть пустым, пока ноды не заведены),
`premium` (слот аккаунта), `personal` (своя машина юзера). Вид **не выводится из имени**: шард
`premium-eu` не становится премиум-слотом сам по себе. Пустой `core`-шард имеет право минтить
коннекты v1, `premium`/`personal` — только вместе со своей нодой.
Ключ иммутабелен: переименование ломает гранты, пиры, подсеть и конфиги нод.

Понять, что такое `0001`, без чтения ключа:

```sql
SELECT * FROM shard_overview;
-- shard | title          | plan     | pools   | nodes | peers_live | address_hosts
-- 0001  | Standard NL/DE | standard | {de,nl} | 3     | 210        | 506
```

`GET /status` отдаёт у каждой ноды `env` и `env_title`:

```bash
curl -s https://api.frkn.org/status | jq '.response[] | {hostname, env, env_title, pool}'
```

В конфиге ноды `shard = "0001"` — алиас `env`, оба ключа равнозначны.
Пользователю имя шарда не показывается никогда: карточка рисуется по `pool_translation`,
заголовок группы — по `plan_title`.

### Протоколы шарда объявляет он сам

Список протоколов шарда нигде не настраивается: это **инбаунды его serving-нод**
(`inbounds.tag` нод, у которых `status` обслуживающий). `announced_inbounds` собирает карту
`env → {tags}`, и от неё зависят три вещи:

1. **грант** — `assign_grant` / `fulfil_plan_grant` сужают запрошенный список до того, что
   выбранный `env` реально анонсирует. Раньше список склеивался по всем `enabled_conns`
   (`map.values().flatten()`), и в пир-шард попадали `vless_*`/`hysteria2`, которых там нет:
   грант обещал карточки, которые не из чего собрать, а v1-плоскость минтила конфиги, на
   которые не отвечает ни одна нода. UPSERT только объединяет протоколы, поэтому мусор ещё и
   не рассасывался сам;
2. **креденшл** — `ensure_granted_creds` минтит `Connection` для каждой client_config-карточки
   гранта (`CardProto::from_tag(..).kind() == ClientConfig`), а не для захардкоженной пары
   `hysteria2` + `vless_xhttp_cdn`. Новый прокси-протокол в шарде начинает работать без правки
   кода — достаточно, чтобы нода объявила инбаунд;
3. **карточка** — `pool_cards` берёт ноды `env`, у которых есть этот инбаунд.

Порядок при заведении нового пула: поднять инбаунд на нодах → нода регистрируется и
попадает в `announced_inbounds` → положить тег в грант (или он уже там) → клиент дёргает
`/v1/locations`, и `Connection` с токеном создаётся сам.

Фильтр **fail-open** намеренно: пустая карта `announced` (снапшот меша не загружен после
рестарта) или `env`, у которого нет ни одной serving-ноды, — это временное состояние, а не
«ничего не обслуживаем». Срезать грант в такой момент значит отнять права у платящего, поэтому
запрос проходит как есть.

## Админский провижининг шардов

Шард объявляется **конфигом** (применяется при старте) либо ручкой, без SQL:

```toml
[service.peers.subnets]
"0001" = ["10.88.0.0/16"]     # только там, где шард наш и диапазон выбираем мы

# Шарды, которых заранее неизвестно сколько (premium-слоты, машины юзеров),
# нигде не перечисляются: api вырезает каждому свой /16 из пула при первом
# обращении (POST /v1/peers), EXCLUDE-констрейнт не даст двум шардам пересечься.
auto_subnet_pool = "10.128.0.0/9"
auto_subnet_prefix = 16
```

Шард без объявленного блока берёт подсеть **у самой ноды** при регистрации: нода принесла
`Address = 10.222.5.1/24` — этот диапазон становится блоком шарда (пересечение отобьёт
`EXCLUDE`). Если диапазон уже занят другим шардом — регистрация отклоняется с 400, менять
надо конфиг ноды. Пул `auto_subnet_pool` нужен там, где ноду настраиваем мы (premium) и
хотим дать диапазон сами.

[service.peers.shards."0001"]
plan = "standard"
title = "Standard"
# kind не пишется: он выводится из плана
# standard/lite -> core, premium -> premium, selfhosted -> personal
```

```bash
PUT    /admin/api/shards/0001     # {plan,title?,kind?,max_subscriptions?,enabled?}
GET    /admin/api/shards          # все шарды из shard_overview
DELETE /admin/api/shards/0001     # забыть шард; отказ 409, пока есть ноды/пиры, force=1 — снести всё равно
```

## Личный шард own-node аккаунта (`sfNNNN`)

Аккаунт «свои ноды» получает собственный шард с номером: `sf0001`, `sf0002`, … Номер выдаёт
последовательность `selfhosted_shard_seq` при создании аккаунта (`POST /v1/private/account`)
и при первом install-токене, если шарда ещё нет. Номера **не переиспользуются**: имя шарда
живёт в `env_capacity`, `env_networks` и на машине юзера, поэтому отданный номер остаётся за
старым аккаунтом навсегда.

Правила шарда:

| | |
|---|---|
| имя | `Env::Named("sfNNNN")`, без префикса `custom`; в БД — как есть |
| владелец | `subscriptions.scope_env`; имя больше не парсится в uuid |
| грант | на **шард**, не на пул: `POST /v1/access` умеет только env |
| пул | одна нода = один пул; нода без `pool` получает в пул свой hostname |
| вид | `env_capacity.kind = 'selfhosted'` → `ShardKind::Selfhosted`, пустой шард не обслуживается |

Старые аккаунты сохраняют `custompersonal<uuid>`: обе формы считаются личным шардом
(`Env::is_personal`), а владелец legacy-шарда по-прежнему восстанавливается из uuid. Аккаунт
без `scope_env`, у которого уже есть ноды в legacy-энве, при первом install-токене
**усыновляет** свой старый env, а не получает новый `sfNNNN` — иначе его машины остались бы в
шарде, которого не видно в кабинете.

## Как план раскладывается по шардам

Выбор шарда для новой подписки — `pick_shard` (`postgres/peers.rs`). Сначала **sticky**: если у
подписки уже есть живой грант этого плана, он и остаётся — ни продление, ни второе устройство
юзера не переезжают на другой шард. Перебалансировки существующих грантов нет вообще.

Дальше — режим `[service.peers] balancing`:

| режим | правило | что получается |
|---|---|---|
| `growth` (дефолт) | шард берёт не больше своей доли **потока регистраций** за последний час; доля = `max_subscriptions` шарда / сумма капов плана | новый шард набирает постепенно, старые продолжают заполнять свои свободные слоты |
| `equalize` | берётся шард с минимальной долей `used/limit` | новый шард забирает **100%** регистраций, пока не догонит остальные; зато все шарды в итоге на одном проценте |

Разница на живых числах (`0001` = 324/500, добавлен пустой `0002`):

* `equalize` — все новые идут в `0002`, пока он не дойдёт до 324. 176 свободных слотов `0001`
  простаивают всё это время.
* `growth` — примерно 50/50: `0001` доходит до своего капа, когда `0002` на ~35%, дальше `0002`
  забирает всё. Слоты `0001` не простаивают, но доли никогда не выравниваются.

`max_subscriptions` — **soft cap** в обоих режимах: полный шард пропускается, пока есть место в
другом, а если полны все — берётся наименее заполненный по доле (не по абсолютному числу).
Юзеру не отказывают никогда, пока хоть один шард жив.

### Порог заполненности: `soft_pct`

`[service.peers] soft_pct = 85` (дефолт 85, `0` выключает) — шард, дошедший до этого процента
**перестаёт брать новых юзеров, пока есть шард ниже порога**. Это то, что заставляет заполненный
шард отдать поток, а не добивать все шарды синхронно:

| ситуация | `growth` без порога | `growth` + `soft_pct = 85` |
|---|---|---|
| `0001` 90%, `0002` 30% | 50/50 | 100% в `0002` |
| `0001` 90%, `0002` 86% | 50/50 | оба выше порога → менее заполненный |
| все выше 85% | менее заполненный | менее заполненный (юзеру не отказ) |

Гистерезис 5 п.п.: шард, стоящий ровно на пороге, не мигает — он возвращается в ротацию, когда
самый пустой шард опускается ниже `soft_pct − 5` (или поднимается выше, если речь о догоне).
Пока порог отсекает хоть один шард, деление потока (`growth`) **не применяется**: оставшиеся
шарды — единственное место для юзера, и половину потока возвращать на «слишком полный» шард
бессмысленно.

Что важно помнить:

* «Заполненность» считается **подписками** (`subscription_access`), а не нодами и не трафиком.
  Шард из 3 нод и шард из 7 нод с одинаковым `max_subscriptions` выглядят равными, хотя ёмкость
  у них разная — кап задаётся руками в `env_capacity`.
* Шард выпадает из кандидатов молча, если у него нет serving-нод с peer-инбаундом, нет блока
  адресов или `enabled = false`. Проверять `GET /admin/api/shards` и `/status`, а не гадать.
* Окно потока — 1 час. При потоке в единицы регистраций в сутки шарды чередуются почти строго.

## Одинаковые имена пулов в разных шардах

Шарды раскатываются из одного шаблона, поэтому `eu` в `0001` и `eu` в `0002` несут одно имя пула
и один перевод: подписка с грантами на оба шарда даёт две строки «Netherlands», различить
которые можно только по IP внутри карточки.

**Различает их клиент.** Один запрос к `/v1/locations` обслуживает одну подписку, а строку юзер
видит в склейке всех включённых на устройстве подписок — сервер эту склейку не видит и номер
проставить не может. `dopamine` нумерует повторы сам: первый шард остаётся без номера, дальше
`#2`, `#3`.

Серверу важно другое: **у каждого шарда должен быть свой `pool_translation`**. Иначе один шард
отдаёт «Netherlands», а другой — голый `eu`, и никакая нумерация этого не исправит.
`pool_translation` живёт в конфиге ноды (`[node] pool_translation`) и складывается в реестр
`pools`; у шарда, поднятого регистрацией нод, его не будет, пока он не прописан.

## Срок и квота гранта

Грант закрывается **сам** таской `expire_grants`: истёкший `expires_at` или выбранный
`traffic_limit` → грант отзывается, пиры снимаются с нод, v1-коннекты этого шарда удаляются.

Раскладка по планам:

| план | `expires_at` | `traffic_limit` |
|---|---|---|
| `standard` | срок подписки | `NULL` — не ограничиваем трафик |
| `lite` (Super Duper) | `NULL` — бессрочно | квота, дальше `quota_exhausted` |

Грант с `expires_at = NULL` не истекает никогда — это законно только для квотных тарифов.

### Продление: грант не только продлевается, но и возвращается

Грант живёт **своим** сроком, поэтому продление подписки обязано двигать и его.
`expire_grants` пишет в `subscription_access.revoked_reason` причину отзыва, и любое
успешное продление даты (`PUT /subscription` от payment-gw, `POST
/admin/api/subscriptions/<id>/extend` из поддержки, `POST /v1/subscriptions` от Apple
IAP, продление ключом) вызывает `renew_grants`:

- **живой** грант получает новый `expires_at`, если новый срок больше его (назад не
  двигается, `NULL` остаётся `NULL`);
- **отозванный с причиной `expired` или `quota`** возвращается: `revoked_at` и
  `revoked_reason` очищаются, `expires_at` = новый срок, `env`, `pool`, `plan` и
  `protos` те же — человек попадает на **тот же шард**. Квотный грант возвращается
  только если под лимитом снова есть место (`used < traffic_limit`), иначе следующий
  тик `expire_grants` снял бы его опять;
- **отозванный явно** (`user`, `subscription_ended`, любая неизвестная причина) не
  трогается: это решение человека, а не часов;
- строки, отозванные **до** появления `revoked_reason` (причина `NULL`), судятся по
  своему сроку: срок уже прошёл — это было истечение (возвращаем), срок ещё идёт —
  отзыв был намеренным (не трогаем);
- подписка **без грантов** (v1-пользователь) — no-op: создание гранта остаётся
  делом активации, продление его не выдумывает.

Пиры при этом **не разотзываются**: `expire_grants` уже отправил на ноды `Delete`, и
оживлять строку, которой нет в ядре, нельзя. Клиент получает новый туннель обычным
`POST /v1/peers` — с тем же ключом устройства и (обычно) тем же адресом из блока шарда.
В лог пишется `renewal: grant revived for subscription <id> env <env> until <дата>`.

## Адрес живёт в аренде: таска `reap_idle_peers`

Пул адресов шарда конечен, поэтому живой пир — это аренда, а не вечное владение.
Таска `reap_idle_peers` (интервал `[tasks] peer_reap_interval_sec`, по умолчанию
3600 с; порог `[tasks] peer_idle_days`, по умолчанию 90, `0` выключает только
возрастное правило) раз в тик берёт **до `[tasks] peer_reap_max_per_tick`** живых
пиров (по умолчанию 200) и отзывает их тем же путём, что и `POST /v1/peers/delete`:
`revoked_at` в базе, удаление из памяти, `Delete`-сообщение в `PeersUpdates` env —
нода снимает пир из ядра. Если пачка пришла полной (значит, есть хвост), следующий
проход идёт через `[tasks] peer_reap_backlog_pause_sec` (по умолчанию 5 с), а не
через весь интервал.

Пир отзывается, если выполнено любое:

| причина (`revoke_reason`) | условие |
|---|---|
| `idle` | трафик не бронировался `peer_idle_days` дней; отсчёт от `max(peer_traffic.updated_at, peer_watermarks.updated_at)`, а если бронирований не было вовсе — от `peers.created_at` |
| `subscription_ended` | `subscriptions.is_deleted`, либо `expires_at` в прошлом **без живого гранта** на этом env (грант и его пиры закрывает `expire_grants`, таска с ним не соревнуется) — и не traffic-mode, где на балансе ещё есть байты |
| `grant_revoked` | у пары (подписка, env) есть строки `subscription_access`, но ни одной живой, и env не своя (`scope_env`) — это пир, переживший отзыв гранта на офлайн-ноде |

Решение (порог, приоритет причин, `created_at` как fallback) вынесено в чистую
функцию `peers::reap_reason` и покрыто юнит-тестами; таска только собирает факты
из `peer_traffic` / `peer_watermarks` / `subscriptions` и выполняет отзыв. За тик
пишется одна строка в лог:
`reap_idle_peers: revoked N peer(s) — X idle >30d, Y subscription ended, Z grant revoked`.
